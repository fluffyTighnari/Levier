# P11.7：R12 有界 replay 与 close/send 串行化

| 项目 | 内容 |
|---|---|
| 日期 | 2026-11-12 |

| 状态 | 完成 |

## 1. 目标

App 重连补拉时，live 事件会先进入 replay 缓冲。缓冲不能无限增长；
关闭连接与发送消息不能互相绕过。

## 2. 改动

### 2.1 replay 缓冲上限

```text
每 Run：1024 条 / 4 MiB
```

`AppConn.SendRun` 在 replay 期间：

```text
超过上限 → replayBuffer.overflow = true
→ 返回 ErrReplayOverflow
```

`AppHub.Publish`：

```text
ErrReplayOverflow
→ WARN app replay buffer overflow
→ CloseConn
```

客户端重连后可重新 subscribe，必要时走 HTTP `/runs/{id}/events` 补拉。

### 2.2 EndReplay 错误不再忽略

```text
replayWS(...)
EndReplay(...)
  成功 → caught_up
  失败 → REPLAY_FAILED，不发 caught_up
```

### 2.3 Broadcast 走连接串行化

之前：

```go
conn.sink.Send(payload)
```

绕过 `AppConn.Send`，不检查 `closed`，也不与 `SendRun` 共用 `sendMu`。

现在：

```go
conn.Send(payload)
```

统一走 `sendMu + sendLocked + closed`。

### 2.4 wsSink close/send

`wsSink` 增加：

```text
closed bool（与 pending 同一把锁）
Send 在同一把锁内检查 closed + 入队
Close 先置 closed，再 close(done)，再关闭底层连接
写协程每次发送前检查 closed
```

写超时：

```text
SetWriteDeadline(now + 5s)
```

慢客户端或半死连接不会永久阻塞写协程。

## 3. 测试

```text

```

## 5. 风险

| 项 | 影响 | 处理 |
|---|---|---|
| replay 上限触发断连 | 客户端需要重连/HTTP 补拉 | 错误日志可见；订阅协议已有 cursor |
| 1024 条对超长 Run 可能偏小 | 重连时更容易溢出 | 单条事件通常较小；后续可按字节/时长调参 |
| 4 MiB 单连接上限 | 大事件会断连 | 已有行为；客户端应避免超大 payload |
| 断连后事件不丢 | 已落库 | 通过 HTTP events / 重新 subscribe 补拉 |
