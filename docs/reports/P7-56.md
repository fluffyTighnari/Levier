## 3. 请求 ID

- 所有响应带 `X-Request-ID`。
- 客户端可传入合法 `X-Request-ID`，原样回显。
- 合法字符：字母、数字、`-`、`_`、`.`、`:`，最长 128。
- 缺失或非法时由 MW 生成 ULID。
- 错误信封带 `error.request_id`，与响应头一致。
- 请求 ID 同时放入 context，后续日志/追踪可直接读取。

## 4. Body 与 JSON 错误

统一通过 `readJSONBody`：

| 情况 | 状态码 | code |
|---|---|---|
| 超过 `MaxBodyBytes` | 413 | `BAD_REQUEST` |
| 必填 body 为空 | 400 | `BAD_REQUEST` |
| 非法 JSON | 400 | `BAD_REQUEST` |
| JSON 后有多余数据 | 400 | `BAD_REQUEST` |

覆盖：

- `POST /runs`
- `POST /admin/apps`
- `POST /apps`
- `POST /runs/{run_id}/cancel`（可选 body；非法 JSON 不再静默忽略）

所有错误都使用同一信封：

```json
{
  "error": {
    "code": "BAD_REQUEST",
    "message": "invalid JSON body",
    "request_id": "01..."
  }
}
```

## 5. Sessions REST

新增 runstore：

```go
GetSession(ctx, sessionID) (Session, error)
ErrSessionNotFound
```

新增可选接口 `SessionStore`，由 `*runstore.Store` 自动满足。

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/api/v1/sessions/{session_id}` | 返回 `SessionView` |
| GET | `/api/v1/sessions/{session_id}/events` | 跨 run 事件补拉 |

- App key 只能读取自己的 session；其他 App 返回 404 `SESSION_NOT_FOUND`。
- Admin token 或 legacy bearer 可读取任意 session。
- 未配置 session store 返回 501。
- session events 支持 `after_attempt`、`after_seq`、`limit`，响应带 `caught_up` 与 next 游标。

- `/healthz`

- `/runs/{run_id}/cancel`

## 8. 风险与未完成

| 项 | 影响 | 处理 |
|---|---|---|
| legacy bearer 可跨 App 访问 | 兼容旧部署但权限过宽 | 生产应只配置 App key/Admin token |
| 请求 ID 尚未写入结构化日志 | 关联日志需额外接线 | P8 观测 |
| session 事件游标跨 run 使用 `(attempt, seq)` | 不同 run 的 attempt 可能重叠 | 当前顺序按 run 创建时间 + run_id；后续可加全局游标 |
| 没有 session 创建/更新 REST | session 由 longterm 流程维护 | P9 |
| 没有 CORS/限流 | 公网部署需网关层处理 | P8 安全 |
| body 限制只作用于 JSON REST | WS 帧限制独立 | P7-57 |
| 错误码仍以 `BAD_REQUEST` 为主 | 客户端难以细分 | 后续按需增加 code |
