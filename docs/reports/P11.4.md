## 1. 目标

控制面自己产生的状态变化必须进入事件流：

```text
cancel  → source=mw, RUN_STATUS cancelled
timeout → source=mw, RUN_STATUS timeout
requeue → source=mw, RUN_STATUS queued
```

同时 timeout 必须像 cancel 一样清理剩余任务，避免队列残留 active task。

## 2. 改动

### 2.1 迁移 `0009_mw_events.sql`

```sql
CREATE SEQUENCE run_event_mw_seq ...;

ALTER TABLE run_events
  ADD CONSTRAINT run_events_attempt_positive
  CHECK (attempt >= 1 OR (source = 'mw' AND attempt = 0))
  NOT VALID;
```

原因：

```text
queued Run 还没被调度时 attempt=0
控制面 cancel 仍然需要一条可回放事件
```

### 2.2 `runstore.AppendMWEvent`

```text
事务内锁 runs 行
→ nextval(run_event_mw_seq) + 2^62
→ source = mw
→ attempt / lease_epoch 取当前 Run
→ insert run_events
```

关键决策：

```text
MW 事件不更新 runs.last_event_attempt / last_event_seq
```

这两列是 daemon 流水的 watermark，用于 gap 检测和 replay cursor。
MW 事件使用保留 seq 区间，但不应把 daemon watermark 推到 2^62。

### 2.3 `AppendEvent` 只推进 daemon watermark

```go
if result.Inserted && normalized.Source == "daemon" && ...
```

### 2.4 Control

| 路径 | 新增行为 |
|---|---|
| `CancelRun` | CAS 成功后再发 cancel；写 `cancelled` MW 事件；结构化日志 |
| `handleTimeout` | CAS 后发 cancel；写 `timeout` MW 事件；调用 `cancelTasks`；日志 |
| `requeueRun` | 写 `queued` MW 事件；日志 |
| `appendMWStatus` | 写库 + 向 AppHub 推送同形态 WS event |

Cancel 发送顺序从“先发 cancel 再 CAS”改成“CAS 成功后发 cancel”，
避免对已经终态的 Run 发 cancel。

事件 payload：

```json
{"status": "cancelled", "reason": "user"}
```

## 5. 风险

| 项 | 影响 | 处理 |
|---|---|---|
| MW seq 保留区不参与 daemon watermark | 同一 attempt 内 MW 事件之后的 daemon 事件不会推进 watermark | 控制面事件只在 cancel/timeout/requeue；终态后不再接受有效 daemon 事件 |
| sequence 全局单调 | 不按 Run 分组 | 主键是 `(run_id, attempt, seq)`，全局唯一即可 |
| cancel 先 CAS 后发送 | 发送失败的旧执行可能继续跑 | epoch/status fencing 丢弃其结果；日志可见 |
| 多 MW 实例 | sequence 仍唯一，但事件顺序依赖 DB | MVP 单实例；后续再评估 |
