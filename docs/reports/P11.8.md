## 1. 目标

Harness 的两个问题：

```text
1. 成功重连后退避不重置，短暂断线会留下 30s 延迟
2. 事件把出站队列塞满时，心跳/Ack 排在后面，MW 误判 daemon 离线
```

## 2. 改动

文件：`harness/src/middleware_harness/channel/client.py`

### 2.1 退避重置

新增配置：

```text
reconnect_stable_after = 5.0s
```

`_session()` 返回是否成功建立过流；`_run()` 统计会话时长：

```text
connected && duration >= reconnect_stable_after
→ delay = reconnect_initial
```

短暂抖动仍按指数退避，稳定连接后恢复 initial。

日志增加：

```text
session_seconds
delay_seconds
```

### 2.2 控制消息与事件分流

之前只有一个 256 容量队列，事件会把心跳/Ack 堵住。

现在：

```text
_control   64 条：hello / heartbeat / task_ack / tool_call_result / error
_outbound 256 条：event / checkpoint / 其他
```

`_writer` 优先取控制队列，再取事件队列；两个都空时用
`asyncio.wait(FIRST_COMPLETED)` 等待。

### 2.3 重连清理

连接建立后丢弃上一会话残留的控制消息：

```text
_drain_control()
```

事件不清空：它们可能仍属于当前 attempt，MW 端有 epoch/seq 校验。

### 2.4 取消清理

`_next_envelope` 被取消时：

```text
cancel control_get / event_get
gather(return_exceptions=True)
```

避免 writer 重启后残留后台 get task。

## 4. 端到端发现的问题（已修）

第一次 retrofit-e2e 失败：

```text
event seq gap: 15/16/15
missing seq 1 = RUN_STATUS running
```

根因不是 MW：新的双队列 writer 用两个并发 `Queue.get`，
当控制消息（TaskAck）和事件（RUN_STATUS running）同时就绪时，
`asyncio.wait` 同时返回两个结果，代码只取一个，另一个已经从队列取走但被丢弃。

修复：

```text
不再并发 get
writer 单循环：
  优先 _control.get_nowait()
  再 _outbound.get_nowait()
  都空 → clear wakeup → 再检查一次 → await wakeup
send() 入队后 set wakeup
```

这样控制消息仍优先，但事件不会被丢掉，也不需要用私有队列操作重排。

证据：

```text
docs/reports/artifacts/P11.8/seq_gap_evidence.txt   失败 Run 的 15 条事件
docs/reports/artifacts/P11.8/retrofit_e2e.log       修复后 PASS
```

## 6. 风险

| 项 | 影响 | 处理 |
|---|---|---|
| 控制队列满仍会阻塞 | writer 完全卡死时无解 | 控制队列独立，容量 64；指标/日志可见 |
| 事件队列满会反压 Run | 不丢事件，但会拖慢执行 | 这是有意的背压；MW 端有缓冲/丢弃策略 |
| 旧事件跨会话保留 | 重连后可能先发旧事件 | MW 用 attempt/epoch/seq 丢弃旧数据 |
| 稳定阈值 5s | 断线抖动判断 | 可配；短暂抖动仍指数退避 |
