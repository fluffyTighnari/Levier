## 1. 目标

一个工具实现 panic 不能杀死 Middleware，也不能让 single-flight 永久卡住。

## 2. 改动

### 2.1 panic 隔离

`Invoke` 的 owner 路径改为：

```text
acquire
→ 二次检查缓存
→ executeSafe
   → defer recover
   → TOOL_EXEC_ERROR
   → 缓存该结果
→ finish
```

panic 日志包含：

```text
run_id / invocation_id / tool_name / panic / stack
```

### 2.2 acquire 后二次检查缓存

```text
get()        miss
acquire()    owner
get()        hit  → finish(f, cached) → 返回
```

避免 get/acquire 之间另一个 goroutine 已完成并写入缓存时产生第二个 owner。

### 2.3 取消与超时区分

| 情况 | 错误码 | retryable |
|---|---|---|
| 等待者 `context.Canceled` | `RUN_CANCELLED` | false |
| 等待者 `context.DeadlineExceeded` | `TOOL_TIMEOUT` | true |
| local 返回 `context.Canceled` | `RUN_CANCELLED` | false |
| global 返回 `context.Canceled` | `RUN_CANCELLED` | false |
| global 超时 | `TOOL_TIMEOUT` | true |

### 2.4 工具超时上限

```text
maxToolTimeout = 4m
```

- HTTP `CreateRunRequest.Timeouts.ToolMS` 超过 240000 → 400
- App 注册的 `tools[].timeout_ms` 超过 240000 → 400
- Gateway 兜底 clamp 到 4m

4m 小于 invocation stale takeover 的 5m，避免“工具还在跑，另一个 worker 已接管”。

## 3. 测试

```text

```

断言：

```text
panic → TOOL_EXEC_ERROR，不抛出，flight 清空
重复 invocation → 命中缓存，不再 panic
等待者取消 → RUN_CANCELLED / 不可重试
工具超时 → 被 clamp 到 4m
HTTP 校验拒绝超大 tool_ms
```

## 5. 风险

| 项 | 影响 | 处理 |
|---|---|---|
| panic 被转成可缓存错误 | 同一 invocation 重试会立即得到错误 | invocation_id 每次调用唯一；需要重试时由上层换新调用 |
| 4m 上限 | 超长工具会被截断 | 需要更长工具时调大 `maxToolTimeout` 并同步 `staleAfter` |
| stack 日志较大 | 日志量增加 | 只在 panic 时输出，便于定位 |
