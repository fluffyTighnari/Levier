## 4. 发送策略

### ephemeral

- 非阻塞写入 sendCh。
- 队列满：
  - 直接丢弃
  - `droppedEphemeral++`
  - 返回 nil
- `Hub.DroppedEphemeral(daemonID)` 可查询。

### 控制 / 持久

- 写入 sendCh。
- 队列满时最多等待 `SendTimeout`（默认 100ms）。
- 等待期间有空间则成功，并清除 slow 标记。
- 超时：
  - 设置 slow 标记
  - 启动 `SlowConsumerTimeout`（默认 5s）定时器
  - 返回 `ErrBackpressure`
- 定时器到期且仍 slow：
  - 关闭连接
  - 触发断线清理

控制消息不会被静默丢弃；调用方会收到错误并决定重试/重排队。

## 5. 单写 goroutine

每个 daemon 仍只有一个 `writeLoop`：

```text
sendCh → writeLoop → stream.Send
```

gRPC stream 写不并发。

## 7. 风险与未完成

| 项 | 影响 | 处理 |
|---|---|---|
| writeLoop 仍可能阻塞在 stream.Send | 极端 gRPC 写阻塞时无法靠队列检测 | 后续加写超时/连接重建 |
| 没有优先级队列 | 控制消息仍与持久事件共享 FIFO | P6/P8 评估 |
| ephemeral 丢弃只计数 | 调用方不知道丢弃 | 指标/日志 |
| 慢消费者只在发送超时时触发 | 没有持续监控 | P6-45 心跳/容量 |
| `ErrSlowConsumer` 暂未单独返回 | 目前统一 ErrBackpressure | 后续错误码细分 |
| 队列固定 256 | 没有按流量动态调整 | 配置化 |
