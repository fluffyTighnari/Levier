## 3. ws_token

| 项 | 行为 |
|---|---|
| 默认 TTL | 10 分钟 |
| 绑定 | `app_id` |
| 存储 | 进程内 map |
| 签发 | `POST /runs` 响应附带；`POST /ws-token` 重新签发 |
| 校验 | 连接时校验存在、未过期、app_id 匹配 |
| 过期清理 | 签发时顺带清理已过期 token |

重新签发：

```http
POST /api/v1/ws-token
Authorization: Bearer <app_api_key>
```

响应：

```json
{"ws_url": "/api/v1/ws", "ws_token": "...", "expires_in": 600}
```

- App key 自动绑定自身。
- Admin/legacy bearer 必须带 `?app_id=`。
- token 过期后连接请求被拒绝；已建立的连接不因 token 过期而断开。

## 4. WS 连接与订阅

连接：

```text
GET /api/v1/ws?app_id=<app_id>&token=<ws_token>
```

- token 无效、过期或 app_id 不匹配直接关闭。
- subscribe 校验 Run 属于该 App，否则返回 `RUN_NOT_FOUND`。
- 支持的客户端消息不变：`hello`、`subscribe`、`local_tool_result`、`ping`。
- `ping` 返回 `pong`。

## 5. 补推

`subscribe` 携带 `last_attempt` / `last_seq`：

1. 从 `run_events` 读取游标之后的事件。
2. 每页 1000 条，持续分页直到不足一页。
3. 逐条发送 `event`。
4. 最后发送 `caught_up`，携带最终 `(attempt, seq)`。

因此超过 1000 条的事件不会被截断。

## 6. 不重不漏

连接内维护每个 Run 的 `(attempt, seq)` 游标：

```text
BeginReplay(run_id, cursor)
Subscribe(run_id)
  ├─ 实时事件 → 缓冲
  ├─ 分页补推 → SendReplay（更新游标）
  └─ EndReplay(watermark)
        ├─ 丢弃 <= watermark 的缓冲事件
        ├─ 按到达顺序发送更晚的事件
        └─ 恢复实时直发
```

- 所有事件发送经过连接级发送锁，补推与实时发送不会交叉乱序。
- 补推期间到达的实时事件先缓冲，结束时按游标去重。
- 补推结束后再收到的旧事件（`<= cursor`）直接丢弃。
- `run_completed` 不携带 `seq`，不参与游标比较。

## 8. 风险与未完成

| 项 | 影响 | 处理 |
|---|---|---|
| token 存于单进程内存 | 多实例部署需共享存储或粘滞路由 | P8 多实例设计 |
| 没有主动撤销 token | 泄露的 token 在 TTL 内可用 | 后续加 revocation |
| token 过期不影响已建连接 | 长连接可继续使用 | 可加连接最大生命周期 |
| `caught_up` 与补推后实时事件的相对顺序 | 极端情况下事件可能晚于 caught_up | 事件仍会送达，不丢失 |
| WS 没有服务端 ping/空闲超时 | 半开连接可能占用资源 | P8 心跳 |
| 没有 WS 帧大小/速率限制 | 大消息/刷屏风险 | P8 安全 |
| `run_completed` 不参与游标去重 | 重连时可能重复收到终态通知 | 客户端应按 run 幂等处理 |
| 事件补推每次订阅重新查库 | 大量历史事件时有数据库压力 | 后续可加快照/缓存 |
