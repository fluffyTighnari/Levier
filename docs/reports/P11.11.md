## 1. 目标

把 liveness 与 readiness 分开：

```text
/healthz  进程活着       永远 200
/readyz   PostgreSQL 可用 200 / 503
```

避免 DB 断连时编排器仍认为实例健康。

## 2. 改动

### 2.1 HTTP

`httpapi.Config` 增加：

```go
ReadinessCheck func(context.Context) error
```

新增路由：

```text
GET /readyz
```

行为：

```text
nil check          → 503 degraded / database=not_configured
check 成功         → 200 ready / database=up
check 失败/超时    → 503 degraded / database=unavailable
```

检查超时：2 秒。

`/healthz` 保持：

```json
{"status":"ok"}
```

### 2.2 启动 wiring

`cmd/middleware/main.go`：

```go
ReadinessCheck: func(ctx context.Context) error {
    return db.Health(ctx, pool, cfg.Database.HealthTimeout.Std())
},
```

不把具体 DB 错误暴露给探针。

### 2.3 OpenAPI 与计划

- `docs/api/openapi.yaml` 增加 `/readyz`，声明 200/503。
- `docs/IMPLEMENTATION_PLAN_V2.md` P0-07 的验收改为
  “`/readyz` 能检查 DB；`/healthz` 保持 liveness”。

## 5. 风险

| 项 | 影响 | 处理 |
|---|---|---|
| 探针配置错误 | 把 `/readyz` 配成 liveness，DB 抖动会重启 Pod | 部署时必须 `/healthz` 做 liveness、`/readyz` 做 readiness |
| readiness 只查 DB | 不检查队列/daemon | MVP 范围；队列故障仍由 API 503 与指标体现 |
| 2 秒超时 | DB 慢时探针失败 | 与 `database.health_timeout` 独立，避免探针拖太久 |
