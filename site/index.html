01

接入成本：一层声明

业务函数不改
你已有的项目 保持原样 
def mark_shipped(order_id: str) -> dict:
    order = repo.get(order_id)
    order.status = "shipped"
    repo.save(order)
    return {"ok": True, "carrier": order.carrier}

测试、调用方、部署方式都不变。

  • 0 行业务逻辑改动
  • 1 个适配进程
  • 1 条WebSocket 连接
  • 1 套版本化契约
+
新增：agent_bridge.py 约 20 行 
from levier_app import LevierApp
from myproject.orders import mark_shipped


def register_tools(app):
    @app.tool(
        "orders_mark_shipped",
        description="把订单标记为已发货",
        schema={
            "type": "object",
            "properties": {"id": {"type": "string"}},
            "required": ["id"],
        },
    )
    def handler(arguments):
        # 只做参数转换，业务逻辑仍在原函数里
        return mark_shipped(arguments["id"])


if __name__ == "__main__":
    raise SystemExit(LevierApp.run_cli(register_tools))

新增一个进程；原服务不需要改。

凭据、重连、工具声明、调用帧与超时映射都由 SDK 处理。你只写 handler， 以及它背后原本就存在的业务函数。 App SDK →

02

一次 Run，你只需要看四件事

细节在文档里
  1. 01

    提交

    从你的 App 或 CLI 发起，带上 prompt 与 runtime_name。返回一个 run_id。

    prompt + runtime
  2. 02

    调度

    Levier 选择一个健康的 Runtime 并分配租约。Runtime 掉线，Run 会重新排队。

    queued → assigned
  3. 03

    调用

    Runtime 跑模型循环。模型要调工具时，local 工具走 App WebSocket，MCP 工具走共享进程。

    TOOL_CALL_BEGIN
  4. 04

    收敛

    结果与事件落库并推送给 App。终态不可逆，可以回放。

    completed / failed
会看到的事件
RUN_STATUS MESSAGE_DELTA TOOL_CALL_BEGIN TOOL_CALL_END ERROR
终态：completed · failed · cancelled · timeout

attempt、lease_epoch 与 fencing 是内部实现，接入时不需要理解。 需要排查并发或重复执行时，再看 架构文档。

04

边界清楚，才好接入

MVP 范围

Levier 负责

  • Run 生命周期与终态
  • 调度、租约与掉线重排
  • local / global / MCP 工具路由
  • 事件持久化与推送
  • 凭据引用与模型 provider 目录

你负责

  • 业务状态与数据
  • 工具处理函数
  • 你自己的业务界面
  • 模型 prompt 与运行策略
  • MCP Server 本身

MVP 不包含

  • sandbox runtime
  • 多实例 / HA
  • 工具 exactly-once
  • 长期 checkpoint 续跑
  • 业务 UI 或工作流编辑器

唯一对外承诺是契约：AppPort（HTTP / WebSocket v1）与 DaemonPort（gRPC v1）。 默认 Runtime 与 MCP 组件随产品交付，都可以按契约替换。 架构与已知缺口 →
